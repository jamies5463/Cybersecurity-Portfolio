**Incident report analysis**

| Scenario | This is an assignment for my portfolio, and the incident described and organisation involved are fictional. In this example I am a Cybersecurity Analyst working for a multimedia organisation, Umberleigh Multimedia Solutions (UMS), offering web design services, graphic design and social media marketing solutions to small businesses. In this scenario the organisation was the victim of a Denial of Service (DoS) attack. Although the organisation makes use of an IT MSP, its role is to install hardware and respond to problems when tickets are raised and does not provide network monitoring and security. |  |  |
| :---- | :---- | ----- | ----- |
| **Summary** | On the 16/09/2026 at 0910 several members of staff reported that they were unable to access internal organisation services such as emails, specialist software and the Human Resources portal. The outage lasted for two hours before critical systems were restored. The organisation’s Cisco Meraki network monitoring dashboard showed a large amount of incoming traffic, saturating the bandwidth. Perimeter firewall logs were analysed to understand the nature of the incoming data packets, which showed a large number of Internet Control Message Protocol (ICMP) Echo Requests, also known as “pings”.  Perimeter firewall logs recorded an average of 400,000 pings per minute targeting the organisation’s public IP address. Pings were sent from around 18,000 different IP addresses, with the same IP address often being used multiple times. This information is indicative of an ICMP flood attack, a type of Denial of Service (DoS) attack. In an ICMP flood attack, an attacker exploits the ICMP echo request, a message sent between computers to confirm the other is online and reachable. The attacker sends a large number of these requests, each of which generates a response, overwhelming the recipient and leaving it unable to provide other services. The team responded by configuring the firewall to temporarily block all ICMP packets, before restoring critical systems, reconfiguring the firewall to allow to restrict the number of ICMP packets allowed through the perimeter firewall, and implementing new measures to harden network security. |  |  |
| Identify | The network was targeted with an ICMP flood attack, a type of DoS attack, affecting the entire network . All systems went offline and had to be restored. The Incident Management Team audited the organisation systems, finding that the ICMP pings targeted the organisation’s public IP address, saturating the inbound bandwidth and disrupting internal services owing to a poorly configured perimeter firewall. |  |  |
| Protect | Two measures were put in place to protect the organisation during the attack: The perimeter firewall was configured to block all incoming ICMP packets. Non-critical services were taken offline. Additionally, several measures were implemented to protect against a future DoS attack after systems had been restored: **ICMP rate limiting.** Following the resumption of critical services, the perimeter firewall was reconfigured to limit the rate of incoming ICMP packets to a level that would not overwhelm the system, reducing the impact of  a similar attack in future. **Source IP Address Verification**. The perimeter firewall was also configured to check for invalid IP addresses. These fall into two broad categories: private blocks and loopback ranges. The former are an agreed set of IP addresses only for use within networks comprising 10.x.x.x, 172.16-31.x.x and 192.168.x.x. As they are for internal use only, any packet arriving from the internet with a source address in these ranges is spoofed and can be blocked. The loopback range is 127.x.x.x and is for a device to communicate with itself, therefore if an IP in this range is accessing the network from outside, it is spoofed and can be blocked. As this measure drops packets before they can cause harm, it has been placed under the Protect domain. |  |  |
| Detect | New measures were implemented to detect similar attacks in future: **Network Monitoring**. The organisation already uses Cisco Meraki network equipment, however the network monitoring dashboard had not been configured to provide alerts for suspicious network activity. Additionally, the network monitoring dashboard was not routinely used except in instances where faults were reported with areas of the network. In response, the dashboard has now been configured to allow for suspicious network activity such as an ICMP flood to be identified. **IDS/IPS**. UMS has upgraded its licence to enable Intrusion Detection System (IDS) and Intrusion Prevention System (IPS), the former alerts in the event that suspicious or malicious traffic is detected, and the latter is able to detect and take action to block such traffic. Crucially, IDS sits within the NIST CSF Detect domain as it is unable to take action. |  |  |
| Respond | Overall, the response followed the organisation’s standard operating procedures (SOPs) in the event of an attack: investigating to identify the cause, containing the threat, prioritising the restoration of systems considered critical to the business in line with SOPs, and investigating the vulnerabilities which allowed the attack and implementing measures to harden vulnerable systems. A review of the SOPs did identify that the preservation of firewall logs and packet capturing for analysis were not explicitly stated, and these have since been added. The vulnerabilities identified were no IPS/IDS capacity, infrequent use of the Meraki dashboard which could have led to earlier identification of the attack, and no out-of-hours network monitoring outside of office hours when the IT team finishes at 1700\.  Given the size of the organisation it is not viable to have its own in-house security operations centre, and the present IT MSP’s scope is only to respond to issues via a ticket system, not to provide network monitoring and alerting. The following measures have been implemented to harden network security: **IPS**. As per the previous section, an IPS has been implemented through pre-existing Cisco Meraki network hardware, this falls into the Respond category as it is able to take action such as dropping harmful data packets. **MSP scope review**. The scope of UMS’ contract with its IT MSP has been reviewed, and the organisation now provides out-of-hours monitoring and response in the event of network issues and attacks. |  |  |
| Recover | Recovery was achieved incrementally as the attack was contained. As above, critical systems were first restored, and once operational and the firewall was shown to be effective in regulating the flow of ICMP packets, non-critical systems were also restored. No data was lost as a result of the attack, and the previous day’s data backup had already happened prior to its commencement. There was significant disruption to the business’ operation and customer work was delayed. This was communicated to customers and information was given of the nature of the attack, with clarity provided that no information had been compromised and no systems damaged beyond the immediate outage. This was communicated quickly to UMS’ Customer Relations Team to address concerns and maintain customer confidence. |  |  |
